## The three live entry filters (as of 2026-09-24)

All three implemented in `workers/entry_filters.py`, checked in order, in both workers, right before a position would open:

1. `is_wash_trading_rejected()` — skip if the token's most recent TIER1 evaluation before the signal was a `WASH_TRADING` rejection.
2. `is_liquidity_too_high()` — skip if that same evaluation reports `liquidity_usd >= $30,000`.
3. `is_buy_pressure_too_low()` — skip if the triggering MomentumSignalEvent's `buy_pressure < 0.97`. The cleanest, most monotonic discriminator found yet (11.7% vs ~35-44% HARD_FLOOR rate) — pure/synchronous, no DB query, since the value is already on the row both workers query.

Skipped candidates are recorded (`status='wash_skipped'` / `'high_liq_skip'` / `'low_bp_skip'`), not silently dropped, specifically so a future analysis pass can measure whether each filter is actually helping. **Read the module docstring for the full numbers before changing any threshold** — they came from analyzing the shadow dataset (262, then 304 trades) against every available metric, not guesses.

## Unsellable positions (as of 2026-09-24)

A position whose real sell keeps failing (confirmed real on-chain rejection, e.g. a fully-drained pool — not a bug on our end) gets downgraded from `status='open'` to `status='unsellable'` after `_UNSELLABLE_AFTER_S` (10 min) of continuous failure. This frees its `CONFLUENCE_LIVE_MAX_CONCURRENT` slot for a new trade (`_open_trade_count()` only counts `'open'`) while it keeps being priced and keeps getting real sell attempts every cycle (`_load_open_trades()` includes both). The **only** way out is a real successful sell — never a fabricated close. Surfaced on the dashboard as a red "⛔ STUCK" badge and a separate `unsellable_trades` count on `/confluence/status`, so stuck money is never just invisible. **Known limitation**: the failure-duration clock lives in-process memory, so a service restart resets it for any currently-stuck position — acceptable for now, but worth remembering if a stuck position seems to "reset" after a deploy.

## Filter calibration self-audit (2026-09-28) — how the bot stays tuned without a human re-running the analysis by hand

Real question the user asked: "how will it stay calibrated on the right filter as time passes and things change?" Honest answer at the time: it didn't — every entry filter threshold is a hand-derived constant from a one-time historical analysis, with nothing checking whether it's still true. Built `engine/filter_calibration.py` to close part of that gap: `workers/confluence_live_worker.py`'s `_maybe_check_filter_calibration()` re-runs the same bucket analysis that validated the 3 filters (win rate / rug rate / capped mean for the population passing `buy_pressure>=0.97` + `liquidity<$30k` + not wash-trading-rejected) on a trailing 14-day window, weekly, and compares against the 2026-09-28 baseline (`BASELINE_WIN_RATE`/`BASELINE_RUG_RATE`/`BASELINE_CAPPED_MEAN` in that file, n=196). On a real divergence (win rate <65%, rug rate >20%, or capped mean turns negative — deliberately generous thresholds, this session's own small buckets showed double-digit swings from noise alone), it fires a `ConfluenceNotification` naming exactly what shifted. On-demand: `GET /confluence/calibration`, and a summary line in `GET /confluence/summary`.

**Deliberately does NOT auto-adjust any threshold** — detect-and-flag only, a human (or a future Claude session) decides what to do with a real divergence. This isn't caution for its own sake: the SAME DAY this was built, this codebase spent hours raising and reverting `_MAX_ENTRY_RENT_OVERHEAD_LAMPORTS` twice (see that constant's own comment in `engine/execution.py` for the full saga) — each raise was backed by real, reasoned, data-driven evidence, and each one still produced a real-money surprise that only live trading revealed. ## Known accounting gap (real, open, low priority but real)

`ConfluenceLiveTrade.pnl_usd` = `exit_proceeds_usd - position_usd` (the *intended* entry size), not the real total lamports debited at entry (which is larger by that trade's token-account rent + network fee). Rent gets fully reclaimed on exit (confirmed working, zero stranded accounts as of 2026-09-24), so it's not a permanent loss — but it means the displayed all-time P&L is somewhat rosier than the true all-in cash-flow picture, especially at these tiny (~$0.03-0.04) position sizes where the fixed ~$0.17-0.18 rent cost per new token account is often bigger than the position itself. Full derivation (real on-chain ledger reconciliation, lamport-exact) is in NOTEBOOK.md's 2026-09-24 "balance reconciliation" sections. Not fixed as of this writing — a real, scoped potential improvement if someone wants to take it on, but don't rush a change to this formula without full test coverage; it feeds the halt-threshold math (`CONFLUENCE_LIVE_MAX_LOSS_PCT`).

## How past improvements got made (the playbook — repeat this)

1. Pull real closed trades (shadow for volume, live for ground truth) joined against `TokenEvaluation` (TIER1's real inputs: age, liquidity, market cap, lp_burn, wash_multiplier, mint/freeze authority, buy_pressure, volume_mult) and `MomentumSignalEvent` (n_rules_cofiring, trailing_return_3min).
2. Bucket by each metric, compute rug rate / capped mean (cap each trade at +100% — a couple of historical trades have unrealistic $0-liquidity "peak" prices that inflate a raw mean) / win rate per bucket.
3. Cross-tab candidate filters against each other before trusting either (a lot of "liquidity" and "LP burn" signal turned out to be the same underlying population — check overlap before claiming two independent filters).
4. Verify a real quote-level sanity check where possible (a dashboard "current price" can be badly stale — see the BLK incident in NOTEBOOK.md — always cross-check a real Jupiter quote before trusting a DexScreener snapshot for anything action-worthy).
5. Implement as a narrow, specific, tested skip condition (see `workers/entry_filters.py`'s two functions as the template), never a broad "block everything TIER1 didn't like."
6. **Watch the status column length.** `ConfluenceLiveTrade.status` and `ConfluenceShadowPosition.status` are `VARCHAR(16)`. A skip-status literal over 16 chars crashed the shadow worker for ~5 minutes the same day the wash-trading filter shipped. Keep new status values short and check `len()` before deploying.
7. Deploy, then watch the *rate limit*, not just correctness — the liquidity guard's first deploy was checking Jupiter's free-tier API too often (3 positions x one check/20s) and got 100% 429'd for several minutes before anyone noticed it was silently providing zero protection. Real external APIs have real limits; a background check that "should be cheap" can still saturate a shared quota.

## Resuming after a blind period (reboot, crash, long gap)

1. `systemctl --user status s1wave-bot.service` — should be `active`. If not, `systemctl --user start s1wave-bot.service` (should also auto-start on boot given it's enabled + linger is on — investigate why it didn't if you find it stopped after a real reboot).
2. `curl -s -u <user>:<password> https://s1wave-solana.duckdns.org/base/confluence/status` (look up current credentials at `/panel/accounts/base` — this file no longer hardcodes them, see the security-incidents section) — check `enabled` (armed or paused?), `wallet_usd`, `open_trades`, `permanently_halted`, `daily_halted`. Don't assume any of these match what an old conversation said.
3. `GET /confluence/live/trades?status=open` — for each open position, get a **real** Jupiter sell quote for its exact `entry_token_lamports` before trusting the dashboard's displayed P&L (see the liquidity-guard/BLK incident — a stale snapshot price can show a fake winner). The guard should be doing this automatically every 60s per position; spot-check it's actually happening (`journalctl --user -u s1wave-bot.service --since "5 min ago" | grep liquidity`) rather than assuming.
4. Check `journalctl --user -u s1wave-bot.service --since "10 min ago"` for anything alarming (`sell_failed_critical`, repeated `quote_error`/429, `cycle_error`) before doing anything else.
5. Only then decide whether to keep operating as-is, pause, or intervene on a specific position.

## Security incidents (keep adding to this, don't let it go stale)

**2026-09-29 — live Basic Auth password committed to this PUBLIC repo.** This file (`CLAUDE.md`) had the base account's real dashboard username/password hardcoded in two example commands, sitting in git history since whenever those lines were first written. `s1wave-bot` is a public GitHub repo (confirmed via `gh repo view`) — anyone who found it had the real credential the whole time. Found while investigating something unrelated (a dead-code cleanup below this same day) — worth remembering that a careless glance at this file is exactly how it surfaced, nothing more sophisticated. Response: rotated the credential immediately (`engine.provisioning.generate_dashboard_credentials`/`update_dashboard_credentials`, the same mechanism the control panel's "Regenerate password" button uses), confirmed the OLD password stopped working (401) before considering it handled, then scrubbed both lines here to point at `/panel/accounts/base` instead of ever hardcoding a credential in a committed file again. **What this does NOT fix**: the old password is still sitting in this file's git history on GitHub forever (rewriting public history is a separate, much bigger, higher-risk operation — force-push, breaks any clone/fork — deliberately not done without an explicit go-ahead). That's an acceptable residual risk ONLY because the credential itself is now dead; if this file is ever found to have leaked something that CAN'T be rotated (a private key, a session secret), history-rewriting becomes non-optional. **Standing rule from here on: never put a real credential value in this file, in NOTEBOOK.md, or in any commit — a placeholder plus a pointer to where the real value lives (the control panel, a `.env` file, a password manager) is the only acceptable form.** Checked the rest of this repo's full git history the same day for the same pattern (Telegram tokens, Solana private keys, other Basic Auth pairs, DB URLs) — this was the only one.
