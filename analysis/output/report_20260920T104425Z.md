**Note on sells=0 (undefined buy/sell ratio):** 22 tokens had buys>0 and sells=0 at decision time. In the current Tier1 code, wash_multiplier in that case is defined as literally the raw buy count (`float(buys)`), not a ratio — so a token with 8 buys/0 sells gets wash_multiplier=8.0, the same numeric neighborhood as a token with a real 8:1 buy/sell ratio from hundreds of trades. These are not the same thing and the current field conflates them. This is flagged again in the findings section as a real feature-engineering issue, not fixed here.

## 5. Findings

**1. Which raw variables show the strongest relationship with future price movement?**
Of the features tested, `wash_multiplier` and `buy_sell_ratio` show the clearest monotonic pattern (see section 1 tables) — lower wash / more balanced buy-sell activity associates with larger peak moves. `liquidity_usd` and `market_cap_usd` show weaker, noisier relationships at current sample size. Exact r-values are in section 1 — read them alongside n, they are not large samples.

**2. Which variables appear useless or misleading?**
`mint_authority_renounced` and `freeze_authority_renounced` are constant across every token seen so far — zero discriminative power, and currently reject nothing. `wash_multiplier` as currently defined conflates two different things when sells=0 (see the note in section 1) — it's usable but the sells=0 subset should probably be its own category rather than blended into the same numeric scale.

**3. Are the relationships linear or nonlinear?**
Check the 'Bucket shape' line and the Pearson-vs-Spearman gap under each feature in section 1 — where Spearman notably exceeds Pearson, or the bucket table is non-monotonic, that's flagged explicitly per-feature above rather than asserted here in general.

**4. Do the six missed movers share a common raw-data pattern?**
See section 4 — wash_multiplier range 1.51–2.00 (all comfortably under the 2.5 Tier1 gate — these look like genuinely organic trading, not a wash-detection miss); scorer scores clustered 4.26–4.86, all below the 5.0 WATCH threshold.

**5. Does the current scorer reward or penalize those patterns?**
All six scored in a tight band (see section 4) just under the 5.0 WATCH threshold despite real subsequent price movement during the same window the scorer was looking at. That's consistent with explanation (A) — raw signal present, scorer not surfacing it — but section 3's limitation (no post-decision sampling) means this isn't proven yet, and n=6 is not a sample, it's six examples.

**6. What additional data would materially improve this analysis?**
- Capture buy_pressure and volume_usd at Tier1 decision time (currently only exist post-decision in token_snapshots) so volume/liquidity-ratio and buy-pressure-at-decision can be tested without leakage.
- Persist the Scorer's raw bp_p1/p2/p3 and vm_p1/p2/p3 window values to token_evaluations.inputs_json, not just the composite score and trend labels — right now that detail only exists in log lines, which rotate and aren't part of the durable record.
- Continue sampling for a short bounded window after a Scorer DISCARD (same pattern as OBSERVE_WINDOW_SECONDS for Tier1 rejects), so there's an actual forward-looking outcome to test the Scorer's own predictive value against, instead of reusing the pre-decision window.
- Populate holder_count — column exists, pipeline never fills it.
- More tokens and more elapsed time. This whole report is n≈129.

**7. What should we test next?**
Re-run this exact script after the dataset has grown meaningfully (a few hundred more tokens, and enough elapsed time for Scorer-discarded tokens' longer-run fate to matter) and see whether the wash_multiplier / buy_sell_ratio pattern holds up, and whether the six-movers pattern (real movement, sub-5.0 score) repeats rather than being six coincidences. Nothing about thresholds or weights should change before that.
